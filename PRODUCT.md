# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

People who farm Diablo II 1.09 with this repository's bots and keep their loot on mule characters.
The maintainer is the first of them. The rest clone the public repo and bring their own accounts,
mule database and machine. They open MuleManager in a desktop browser on the machine that runs the
bots, usually with a concrete question: is there an item for this character, which mule holds it,
and where does the next round of loot fit.

## Product Purpose

MuleManager is the web view of everything the mules hold. It should answer mule questions without
anyone having to ask: search the stock, find the best upgrade for a character's slot, and see and
plan muling. Today the upgrade questions go to Claude through the `mule-items` skill, and the UI is
meant to take that job over. Success means a gear decision or a muling decision can be made from the
UI alone, with the answer the skill would give.

## Positioning

It reads the real stock, not a list someone keeps by hand. The bots' own clientless client logs
into every mule account and stores what each stash and inventory holds, and the farming bots
update the same database after every mule pass. Items are judged by 1.09's rules as this realm
applies them: resist penalties per game mode and difficulty, affix ranges from the patch's own
tables, breakpoints and base requirements. Wikis and later patches are not the source.

## Operating Context

- Runs locally. A Blazor WebAssembly UI (`src/D2NG.MuleManager.UI`) calls an ASP.NET API
  (`src/D2NG.MuleManager`) that reads the mule database (Marten on Postgres). The same database
  feeds the farming bots' muling, the cube bot, `tools/MuleConsolidate` and
  `tools/ClassicToExpansion`.
- "Update mules" logs into every configured mule account in parallel. The realm is shared with any
  running bots and limits game joins per IP, so a refresh competes with them for joins.
- Classic and expansion are separate economies: an item only trades between characters of the
  same game mode. The database does not record the game mode yet, and the `mule-items` skill infers
  it from which mule config lists the account. MuleManager will store the game mode each character
  reports at login in its snapshot (decided 22 Nov 2026).
- MuleManager does not use the realm's armory. What a bot character wears comes from gear snapshots:
  the bots store them as they play, and MuleManager can refresh them itself by logging into the
  accounts listed in its own config, next to the mule accounts.
- The game data the judgements need (`item-affixes.json`, `skills.json`) is generated by
  `tools/MpqData` from the user's own game install into the bot folder's `data`, outside the repo.
- Rounds are planned by `D2NG.Mule/Packing` (room check, stash packer, repack) and carried out by
  the bots.

## Capabilities and Constraints

Today the UI lists every muled item with account, character, base, quality and stats. It filters
by quality, item name, item classification and the stats an item must carry, sorts by one stat,
and can trigger a refresh of all mules.

Confirmed jobs going forward:

- **Browse and search stock** across all mules.
- **Find upgrades**: pick a character and slot and see better items as a change against what the
  character wears, priced in the stats that class lives on, with resists after the difficulty
  penalty, breakpoints and strength/dexterity requirements. This is the logic of the
  `mule-items` skill (`gear`, `items`, `calc`, `combo`), which currently lives in a Python script
  outside the UI and is ported to C# for MuleManager. The first build ranks one slot at a time;
  the combo search, which lets a second slot make up the resists, comes later.
- **Manage muling**: see how much room each mule has and how current its data is, and refresh all
  accounts or one. Transfers and consolidation stay with the bots and tools.
- **Classic versus expansion** stays visible everywhere, so the user never picks an item the
  character cannot receive.

Constraints:

- Works for anyone who clones the repo: no hardcoded hosts, accounts, character names or machine
  paths. The API address is hardcoded to `https://localhost:5001` today and has to become
  configurable.
- The repo is public. Screenshots, fixtures, sample data and docs that get committed carry no
  account or character names and no realm address. Refer to characters by role.
- Anything that destroys items (as `tools/AccountTool drop` does) needs a dry-run preview first,
  and the user approves that exact list before each run.
- Vocabulary is the game's and the database's: quality (Normal, Superior, Magical, Set, Rare,
  Unique, Crafted), ethereal, sockets, item classification, the `StatType` names, and the armory's
  slot names (head, amulet, body, right hand, left hand, right ring, left ring, belt, boots,
  gloves).

Undecided:

- Whether the UI may show game art such as item graphics. If it does, the art has to come from
  the user's own install at runtime, because the repo is public.

## Brand Commitments

- The product is called **MuleManager**, part of the D2NG projects in this repo.
- The current look is MudBlazor's default theme. The user wants better styling than that,
  preferably a Diablo theme (stated 22 Nov 2026). The visual direction itself is not decided yet.

## Evidence on Hand

- The live mule database: real items across every configured mule. It stays local and is never
  committed with names.
- `mule-fixtures/` beside the bot log: JSON snapshots of real mule passes. Rename the account and
  character before committing one.
- The affix reports (`affixes-classic.md`, `affixes-expansion.md`) from `tools/MpqData --report`
  list every affix that can roll, per item type.
- The `mule-items` skill and its script: the worked logic for upgrades, resists and combinations.
- None yet: screenshots of the UI, a logo or other brand assets, feedback from other repo users.
  Do not invent them.

## Product Principles

1. **Answer, don't list.** The UI should settle the question the user brings ("what's the best
   ring for this character?"), not hand over a table to dig through.
2. **An upgrade is a change against the item it replaces.** Show what the character gains and what
   it gives up, resists first, never an item's stats on their own.
3. **Never mix classic and expansion.** Every search, list and plan knows which game mode it is in.
4. **Real items over tables.** The patch tables guide what can roll, but the realm sometimes rolls
   outside them. Never call an item impossible on the tables alone.
5. **Anyone's setup, nobody's names.** Everything works from the cloner's own configuration, and
   nothing personal reaches the repo.
